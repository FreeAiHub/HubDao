## 1. Задача (как я её понял)
- GUI-калькулятор, кросс-платформенный: Windows, Linux, macOS. Android не нужен.
- Помнит **15 последних вычислений**, в том числе после перезапуска.
- **Без лишних программ**: никаких Python, Electron, Java, .NET, Qt.
- **Не больше 5 МБ RAM**.
- Новое требование: собирать всё через **Zig 0.17.1** как единый кросс-компилятор.

## 2. Архитектура

```
             ┌──────────────── src/core.c ────────────────┐
             │ парсер · история · кнопки · отрисовка      │
             │ (вызывает 3 функции платформы)             │
             └───────┬───────────────┬───────────────┬────┘
   plat_fill / plat_text / plat_text_width   core_key / core_mouse_*
             │               │               │
     plat_win32.c       plat_x11.c      plat_cocoa.m
     Win32 + GDI        Xlib            Cocoa (Objective‑C)
     Windows 7+         любой X11/XWayland  macOS 10.13+
```

Почему так:
- Вся логика написана один раз, поэтому на всех ОС калькулятор считает одинаково.
- Слой под ОС — 150–350 строк. Он рисует только прямоугольники и текст.
- Родной API каждой ОС означает минимум памяти и ноль зависимостей.

### Где хранится история
- Windows: `%APPDATA%\MiniCalc\history.txt`. Путь в UTF-16, поэтому работает и с кириллическим именем пользователя.

- macOS: `~/Library/Application Support/MiniCalc/history.txt`.

## 3. Хронология (что реально происходило)
1. Проверил окружение. Нашлись gcc, clang и libX11-dev, MinGW не было, поставил `gcc-mingw-w64`.
2. Спроектировал схему «ядро + 3 слоя».
3. Написал Linux-слой и проверил в Xvfb. Окно работает, но кириллица не рисуется, RAM 5.9 МБ.
4. Оптимизировал шрифты. Xlib держал метрики на 65 536 символов (~800 КБ на шрифт), я оставил только нужные. Стало 4.9 МБ. Если в системе нет кириллических X11-шрифтов, надписи автоматически переходят на английский.
5. Улучшил формат чисел: длинное число показывается с меньшим числом знаков, а не обрезается.
6. Написал Windows-слой. MinGW собрал `.exe` на 56 КБ, зависит только от системных DLL.
7. Поставил Wine 9.0. Окно и кириллица отображаются правильно. Shift-клавиши в Wine из синтетических событий не доходят, но это ограничение теста, а не программы.
8. Написал macOS-слой на Cocoa / Objective‑C.
9. Написал юнит-тесты: 33/33 проходят, в том числе с AddressSanitizer и UBSan.
10. Добавил Makefile, `.bat`, Info.plist и workflow GitHub Actions.
11. Убрал libm, добавил `mallopt` и `malloc_trim`. RAM на Linux: **2.6 МБ RSS / 1.0 МБ PSS**.
12. Проверил мышью: `7 × 8 = 56`, затем «+», клик по истории, «+1 =» дало **113**. История пережила перезапуск.
13. CI — 4 прогона, каждый находил новое:
    - прогон 1: синтаксис YAML (двоеточие в имени шага) — исправлено;
    - коммит без прогона: триггер был только на теги, ветки игнорировались — исправлено;
    - прогон 2: на macOS `mkdtemp` скрыт в режиме `-std=c99` — исправлено;
    - прогон 3: **настоящий баг**: на macOS история не сохранялась, если нет родительской папки. Исправил через рекурсивное создание папок;
    - прогон 4: macOS ✅ (16 МБ footprint), Linux-job ❌: MinGW из Ubuntu 22.04 не знает `WM_DPICHANGED`. **Не исправлено** (прервали).
14. Вы спросили про язык — ответил: C и Objective‑C.
15. Zig 0.17.1 (вышел 2 ноября 2026, это новее моих знаний):
    - скачал и сверил SHA256;
    - `zig cc` с Linux собрал тестовые программы под macOS arm64, macOS x86_64 и Linux glibc 2.28;
    - MiniCalc.exe из текущих исходников собрался на 73 КБ. Ошибки `WM_DPICHANGED` в Zig нет: у него свежие заголовки MinGW.
    - Дальше не пошёл: вы прервали.

## 6. План по Zig 0.17.1 (рекомендую)
Цель: **одна команда `zig build` на любой ОС собирает все три версии**, без MinGW, Xcode и SDK.

1. `build.zig`: цели `x86_64-windows`, `x86_64-linux-gnu.2.28`, `aarch64-macos`, `x86_64-macos`.
2. Windows: всё уже работает через `zig cc` (проверено).
3. Linux: грузить libX11 во время запуска через `dlopen`. Тогда для сборки не нужны `libx11-dev` и X11-заголовки (вложить маленькие MIT-заголовки в репо).
4. macOS: переписать `plat_cocoa.m` на чистый C через Objective‑C runtime (`objc_msgSend` + `dlopen` AppKit). Тогда SDK и Xcode не нужны, Zig собирает с Linux.
5. Universal-бинарник для macOS собирать маленькой утилитой на C (формат fat Mach-O).
6. CI: один job на Linux собирает всё через Zig, а smoke-тесты идут на родных раннерах.

Оценка: 2–4 часа работы агента. Главный риск — macOS-слой без Mac под рукой: проверять придётся только через CI.

## 7. Что вы могли не знать (рекомендации)
- **5 МБ на macOS — физический предел Cocoa.** Пустое окно на AppKit уже занимает ~10–20 МБ footprint. Сам код калькулятора меньше 1 МБ. Варианты: принять это, или мерить только «свою» память процесса.
- **«RAM» меряют по-разному.** RSS включает общие системные библиотеки, а PSS и private — только своё. В Диспетчере задач Windows по умолчанию показывается private working set.
- **Zig 0.17 ≠ язык Zig.** Можно использовать Zig только как компилятор и систему сборки для C-кода (быстро). А можно переписать на языке Zig — это несколько дней, и выигрыша по памяти не будет.
- **Без подписи** Windows и macOS будут предупреждать при первом запуске. Для клиентов CrowHub это важно.
- **Linux-бинарник собран под glibc 2.35** (Ubuntu 22.04). Через Zig можно целиться в glibc 2.17–2.28: тогда запустится даже на старых дистрибутивах.

## 9. Структура и оркестрация

### Как реально работало
- **Один агент** (я) вёл всё последовательно: проектирование → код → проверка → CI.
- Параллельно запускались только фоновые задачи: установка пакетов и ожидание CI.
- **Субагентов не запускал**, в том числе для этого отчёта. Вся информация уже была в контексте этой сессии. 10 агентов начали бы «с нуля», заново читали бы то же самое и потратили бы больше времени, чем 2–5 минут, без новой информации.

### Поток работы
```
Требования → Архитектура → [Linux слой → Xvfb тест → оптимизация RAM]
                         → [Windows слой → MinGW → Wine тест]
                         → [macOS слой → только CI]
           → Юнит-тесты → CI (4 итерации) → Zig 0.17.1 (проверка) → Отчёт
```

### Если нужна команда из 10 агентов (для следующей большой задачи)
| # | Агент | Задача |
|---|---|---|
| 1 | Оркестратор | план, приём результатов, финальный отчёт |
| 2 | Core-разработчик | ядро C, тесты |
| 3 | Windows | Win32-слой, smoke на windows-latest |
| 4 | Linux | X11/dlopen, Xvfb-тесты |
| 5 | macOS | objc-runtime слой, проверка в CI |
| 6 | Build/Zig | `build.zig`, кросс-сборка |
| 7 | CI/DevOps | workflow, артефакты, релизы |
| 8 | QA | сценарии, скриншоты, регрессии |
| 9 | Perf | замеры RAM на 3 ОС |
| 10 | Docs | README, отчёты |

Смысл такая команда имеет на задачах, где агенты работают **независимо** (агенты 3, 4, 5, 6 одновременно). Для сводки уже известной информации она только замедляет.

### Как улучшить (себе)
1. Проверять YAML и триггеры CI локально **до** пуша (`actionlint`).
2. Собирать Windows тем же компилятором, что в CI, или сразу через Zig.
3. Писать короткий статус каждые 2–3 минуты.
4. До старта уточнять неоднозначное: «Zig как компилятор или как язык?», «как мерить 5 МБ на macOS?».
5. Сначала доводить один путь до зелёного CI, потом расширять.
